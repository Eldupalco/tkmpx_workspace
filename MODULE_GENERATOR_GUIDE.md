# Module Generator Guide (`pnpm run gen:module`)

`scripts/generate-module.mjs` scaffolds a typed CRUD feature module from a Prisma model. The schema is read with Prisma's own parser (`@prisma/get-dmmf`), so every field, enum, default and relation comes from the schema. Paths and project features (guard, error filter, response envelope, import style, layout) are detected from the project or set in `gen-module.config.json` (section 4), so the generator also works in other NestJS + Prisma projects.

---

## 1. Usage

```powershell
pnpm run gen:module users                 # one model (singular, plural or PascalCase all match)
pnpm run gen:module users --dry-run       # list files and registration, write nothing
pnpm run gen:module users --force         # overwrite; the old module is backed up first
pnpm run gen:module users --only=dto,views  # after a schema change: refresh DTOs and views, keep service/controller edits
pnpm run gen:module --all --force --spec  # every model, with Vitest smoke specs
pnpm run gen:module audit-logs --public   # no auth guard on the controller
pnpm run gen:module --print-config        # show detected settings and their source
pnpm run gen:module --undo                # revert the last run
pnpm run gen:module --list-backups        # list past runs and what each changed
```

| Flag | Effect |
| --- | --- |
| `--force`, `-f` | Overwrite an existing generated module folder. The old folder and the root module are copied to `.gen-backup/<timestamp>/` first. |
| `--only=<groups>` | Rewrite only these file groups of an existing generated module, backing up each file: `dto`, `views`, `service`, `controller`, `module`, `spec`. |
| `--dry-run` | Print what would be created and registered. Nothing is written. |
| `--all` | Generate every model in the schema. The summary lists generated, skipped and failed models; the exit code is 1 if any failed. |
| `--spec` | Add controller and service specs for the detected test framework (Vitest or Jest). |
| `--public` | Leave out the auth guard and `@ApiBearerAuth()`. |
| `--print-config` | Print every resolved setting, marked `detected` or `config`, and exit. |
| `--undo` | Revert the most recent run that is not yet undone. `--undo=<run id>` reverts a specific run. Combine with `--dry-run` to preview, or `--force` to discard edits made after that run. |
| `--list-backups` | List recorded runs (oldest first) with their command, status and the paths they created or replaced. |

The model must exist in the schema, and the Prisma client must be regenerated (`npx prisma generate`) after schema changes, because the generated services are type-checked against it. Node.js 20.1 or later is required.

**Safety rules**

- The module folder and class names always come from the model name, so `tickets` and `Ticket` produce the same `src/ticket` module, never a duplicate.
- A folder is overwritten only if the generator created it: its module file starts with `// Generated by gen:module` (or, for modules from earlier versions, it has a `*.select.ts`). Hand-written folders such as `src/auth` are never touched, even with `--force`.
- Generation is refused when the module, controller or service class name already exists elsewhere (for example a model named `App` would clash with `AppModule`).

**Undo**

Every run that writes files records itself in `.gen-backup/<run id>/`: a copy of each path it replaced (module folder, `app.module.ts`, single files with `--only`) and a list of the paths it created. `--undo` restores the replaced paths and deletes the created ones, for example a new module folder and the `RolesGuard` file, so `app.module.ts` goes back to its earlier state.

- Undo checks each touched path against its state right after the run. If you edited a file afterwards, or a later run changed the same module, it stops and names the paths. Undo the later runs first, or pass `--force` to discard those edits.
- Runs are undone newest first by default. Each run can be undone once.
- `--undo` covers only generator runs. Use git for anything else; committing before a generator run is still the most reliable safety net.
- Backup folders from versions without undo support are listed as "backup only" and must be restored by copying them back manually.
- `.gen-backup/` is git-ignored and never cleaned up automatically; delete old run folders when they are no longer needed.

## 2. Generated Files

Default (`"layout": "nested"`):

```text
src/<name>/
├── controllers/<name>.controller.ts   REST endpoints, Swagger docs, JwtAuthGuard + RolesGuard, id pipe
├── services/<name>.service.ts         Typed Prisma CRUD, pagination, search, filters
├── dto/create-<singular>.dto.ts       class-validator rules per field type
├── dto/update-<singular>.dto.ts       PartialType of the create DTO (a client-supplied id is excluded)
├── dto/query-<singular>.dto.ts        page, limit, search, sortBy (whitelisted), filters
├── views/<singular>.view.ts           Response docs, including the TransformInterceptor envelope
├── views/<singular>.select.ts         Prisma select shared by every query
└── <name>.module.ts                   Registered in src/app.module.ts automatically
```

With `"layout": "flat"` (Nest CLI style), the controller, service, module and specs sit directly in `src/<name>/`; `dto/` and `views/` stay as subfolders.

**Access control.** With a role claim in the JWT (detected from the `sign(...)` payload, here `role`), any authenticated user can read (`GET`), and create, update and delete require one of `writeRoles` (default `admin`). The first run creates a shared `src/common/guards/roles.guard.ts` (`RolesGuard` and `@Roles(...)`); an existing `RolesGuard` with a `Roles` decorator is reused. Without a role claim, a warning says that any authenticated user can write. Rules per record owner (for example "users may edit only themselves") are not generated and must be added by hand.

## 3. How the Schema Maps to Code

| Schema | Generated behaviour |
| --- | --- |
| `String @id` without default | `randomUUID()` on create, `ParseUUIDPipe` on `:id` |
| `String @id @default(uuid())` | `ParseUUIDPipe`; other string defaults (e.g. `cuid()`) get no pipe |
| `Int @id @default(autoincrement())` | `ParseIntPipe`, `id: number` |
| `@id` without any default (non-string) | Required in the create DTO, not changeable through PATCH |
| `enum` fields | `@IsEnum`, Swagger enum, exact-match filter |
| `Json` | `@IsObject`, `Record<string, any>` |
| `Decimal`, `BigInt` | Accepted as numbers, returned as strings. The service converts `BigInt` values with a generated `serialize()` function. |
| Scalar lists (`String[]`) | `@IsArray` with `{ each: true }` validators, optional on create |
| `Bytes`, `Unsupported(...)` | Skipped with a warning |
| Secret fields: any name containing the word `password`, or ending in `token`, `secret`, `hash`, `salt`, `otp`, `pin`, or `apiKey`/`privateKey`/`accessKey` | Hidden from responses and the select. Judged by whole words, so `tokenCount` and `hashtags` stay visible. |
| Fields named `*password*` | Hashed with argon2, bcrypt or bcryptjs (whichever is installed) on create and update; a warning is printed if none is |
| `createdAt` / `updatedAt` / `@updatedAt` | Left out of DTOs; set to `new Date()` only when the schema has no default |
| Foreign keys (`@relation(fields: [...])`) | Kept in the create DTO and filters, replaced in responses by a summary of the related record (id plus up to three display fields). Contact data (email, phone, address, birth date) and secrets are never included in summaries. |
| Nullable columns | Documented as `nullable: true` in views |

Prisma errors: when a global exception filter for `PrismaClientKnownRequestError` is registered (as in this project), the services do not catch them. Otherwise each service maps P2002 → 409, P2003 → 400 and P2025 → 404 itself.

## 4. Settings and Other Projects

Every setting is detected from the project. Create `gen-module.config.json` in the project root only to override a detected value. Paths are relative to the project root, without the `.ts` extension.

| Setting | Detected from | Example override |
| --- | --- | --- |
| `srcDir` | `nest-cli.json` `sourceRoot`, else `src` | `"src"` |
| `schema` | `schema` in `prisma*.config.ts`, `package.json` `prisma.schema`, else `prisma/schema.prisma` or the `prisma/schema` folder (multi-file) | `"prisma/schema"` |
| `prismaClient`, `prismaEnums` | The `generator` block: `prisma-client` → `<output>/client` and `<output>/enums`; `prisma-client-js` → `@prisma/client` | `"@prisma/client"` |
| `prismaService` | The class that `extends PrismaClient` | `{ "path": "src/db/db.service", "className": "DbService" }` |
| `authGuard` | `"global"` if a guard is provided as `APP_GUARD`; else the `JwtAuthGuard` or `*Auth*Guard` class; else `false` (public). `module` is the non-global module that exports the guard; generated modules import it so the guard's dependencies resolve. | `{ "path": "src/auth/jwt.guard", "className": "JwtGuard", "module": { "path": "src/auth/auth.module", "className": "AuthModule" } }` |
| `accessControl` | A `role` or `roles` claim in the JWT `sign(...)` payload → `{ "roleClaim": "role", "writeRoles": ["admin"] }`; else `false` | `{ "roleClaim": "roles", "writeRoles": ["admin", "manager"] }` |
| `rolesGuard` | An existing `RolesGuard` class and `Roles` decorator; else `<srcDir>/common/guards/roles.guard`, created on first use | `{ "path": "src/auth/roles.guard", "className": "RolesGuard", "decoratorPath": "src/auth/roles.decorator", "decorator": "Roles" }` |
| `prismaExceptionFilter` | A `@Catch(...PrismaClientKnownRequestError)` filter registered with `useGlobalFilters` or `APP_FILTER` | `false` |
| `responseEnvelope` | An interceptor registered with `useGlobalInterceptors` or `APP_INTERCEPTOR` that returns `{ success, statusCode, data }` | `false` |
| `importExtension` | tsconfig `module`/`moduleResolution` set to `node16`/`nodenext` → `".js"`, else `""` | `""` |
| `layout` | Existing modules with a `controllers/` folder → `nested`, with `<name>.controller.ts` → `flat` | `"flat"` |
| `appModule` | `<srcDir>/app.module.ts` | `"src/app.module.ts"` |
| `passwordHashing` | `argon2`, `bcrypt` or `bcryptjs` in dependencies, else `false` | `"bcrypt"` |
| `testFramework` | `vitest` or `jest` in dependencies, else `false` | `"jest"` |
| `format` | `prettier` in dependencies | `false` |

Example `gen-module.config.json` for a Nest CLI project on the classic Prisma client:

```json
{
  "layout": "flat",
  "prismaClient": "@prisma/client",
  "prismaEnums": "@prisma/client",
  "authGuard": false
}
```

The generator also prints a warning on every run when:

- no global `ValidationPipe` is found, or it lacks `whitelist: true` (clients could then set any column) or `transform: true` (numeric and boolean query filters stay strings);
- `@prisma/get-dmmf` and `prisma` differ in major or minor version.

**Using it in another project**

1. Copy `scripts/generate-module.mjs` and the `scripts/generate-module/` folder.
2. Install the schema parser at the same version as the project's `prisma` package, for example `pnpm add -D @prisma/get-dmmf@7.10.1`. `typescript` must also be installed.
3. Add `"gen:module": "node scripts/generate-module.mjs"` to the `package.json` scripts.
4. Run `pnpm run gen:module --print-config`, check the detected values, and add `gen-module.config.json` for any that are wrong.
5. The generated code needs `@nestjs/swagger`, `class-validator` and `class-transformer`.

## 5. Verifying Generator Changes

```powershell
pnpm run gen:verify
```

This first checks app-module registration, generator detection, naming, secret-field detection and multi-file schemas. It then runs two scenarios in scratch copies under `.gen-verify/`, each with the edge-case models from `scripts/generate-module/fixtures/edge-cases.prisma` added:

- **detected**: this project's own setup. In addition it compiles the app and runs `fixtures/http-probe.mjs`, which boots `AppModule` with a stubbed Prisma client and checks real HTTP behaviour (401 without a token, 403 for writes by non-admins, 201 for admins, 400 for an invalid `sortBy`, id or PK change, BigInt returned as a string, no email in relation summaries). It also checks that models named `App` and `Auth` are refused, that `tickets` reuses `src/ticket`, and that `--undo` restores an overwritten module (including a hand edit), removes a new module with its `app.module.ts` registration, and refuses to discard later edits without `--force`.
- **portable**: a different project setup (flat layout, no guard, no exception filter, no envelope, no hashing, bundler-style imports without `.js`).

Each scenario runs `prisma generate`, generates every module, checks key output, and runs `tsc`, `oxlint --deny-warnings` and the generated specs. `src/` is not touched. Add `--keep` to inspect the scratch copies afterwards.

Run it after every change to the generator.

| `scripts/generate-module/app-module.mjs` | AST-based registration in `app.module.ts` |

| `scripts/generate-module/templates/*.mjs` | DTO, view/select, service, controller, module, spec and RolesGuard templates |

## 7. Removing a Generated Module

1. Delete the module folder (`src/<name>/`).
2. Remove its import and its entry in `imports: [...]` from the root module (`src/app.module.ts`).

If the module was created by a recorded run that is still the latest, `pnpm run gen:module --undo` does both steps.
